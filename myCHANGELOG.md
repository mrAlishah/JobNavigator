# myCHANGELOG

Changes made in this fork on top of upstream JobNavigator. Upstream's own release history stays in
[CHANGELOG.md](CHANGELOG.md); do not record fork changes there.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

Last merged with `upstream/main` on 2026-10-22 (20 commits after the 2026-10-19 merge: one API key per provider, one-at-a-time scrapes with a Waiting state, the shared search-mode registry, résumé rename from the top bar, multi-arch images). The fork branched at `3be5ab1` (2026-10-15, after upstream 2.2.0). Where the two sides disagreed, the fork's behaviour was kept and upstream's account scoping, sandboxed rendering and safe filenames were wired in around it; the one exception is Rename, where upstream's inline top-bar rename replaced the fork's dialog. Everything below exists only in this fork.

**Merging upstream.** Do not merge into `mydevelop` directly. Create a dedicated worktree and feature branch from `mydevelop` HEAD (for example `git worktree add ../merge-upstream-YYYY-MM-DD -b merge/upstream-YYYY-MM-DD mydevelop`), run `git merge upstream/main` there, resolve conflicts and verify, then bring the result into `mydevelop` only after review. Risky maintenance work (refactors, dependency or schema changes) follows the same rule. Verify with the CI-identical checks: `DATABASE_URL=sqlite:///:memory: pytest backend/tests/` on Python 3.12 in a venv outside the repository, `ruff check backend/ --select=E9,F63,F7,F82`, and `npx vitest run`, `npx vite build` and `python3 tests/tools/stylelint.py` (clean: any finding is new). After `git fetch upstream`, and again after the merge, run `python3 tests/tools/docx_parity.py`: it builds the Word export with upstream's `_build_docx` and the fork's on 22 inputs and fails on a guard the fork lost or a difference in text, links or headings, because an upstream fix to that function arrives as a conflict that is easy to resolve in the fork's favour and lose. `backend/tests/test_fork_golden.py` pins the rendered HTML of every template, the Word export structure and the API surface; if it fails after a merge, find out whether upstream's change or the merge caused it, and regenerate with `python -m backend.tests.fixtures.generate_fork_golden` only once the new output is the intended one, then review the diff of the three `fork_golden_*.json` files. Extracting fork code into separate modules was measured on 2026-10-22 (hunks that edit upstream lines stay: `routes_resumes.py` 18, `ResumeEditor.jsx` 5; the extractable blocks are mostly pure insertions that merge cleanly unless upstream edits next to them) and was not done; the smaller candidates (the profile-image upload at the end of `routes_settings.py`, the profile-image row in `Settings.jsx`) have a modest gain, so revisit them if a merge conflicts there.

**Template ownership.** Fork-owned: `backend/resume_templates/professional-top-left-image` and `professional-top-right-image` (folder, `meta.json`, Manrope fonts); nothing else. Upstream-owned: the other eight folders. Seven of them (`garamond_alt`, `inter`, `modern`, `montserrat`, `palatino`, `raleway`, `traditional`) are byte-identical to upstream; `helvetica` is the one documented exception (it still carries the old print-layout and heading edits, plus a one-line `section_titles` default, because restoring it would change its PDF's right margin from the fork's current 0.71in to 0.55in (equal to the left), a visible change that has not been reviewed: compare the two PDFs, then `git restore --source=upstream/main -- backend/resume_templates/helvetica`). The fork's behaviour on the official templates is applied to their rendered HTML by `backend/resume_template_overrides.py`, called from `_render_html` in `backend/api/routes_resumes.py`: the footer's reserved bottom band and entries kept whole across pages (`print_layout`, which reads the template's own `@page` margins), and custom section headings, including adding a Summary heading to the templates that have none (`section_titles`). A function is skipped for a template that reads `footer_reserved_in` / `section_titles` itself, so the Professional templates and helvetica are never adjusted twice, and a new upstream template needs no registration or patch. "Reads" is what Jinja's parser says (`reads()` in the same module, `meta.find_undeclared_variables`, following `{% include %}`d and imported partials): a comment or a string that mentions the name does not count. A partial that is missing or has a dynamic name cannot be told, and the overrides stay on, since they only touch the structures they recognise. Custom headings are swapped in one pass, so a title equal to another section's default name is kept as written. The Professional templates connect to the shared code only through their `meta.json` (`docx` block, `style_overrides`), the `profile_image_path` text check for `has_profile_image`, and the render variables `style_css`, `footer_reserved_in`, `section_titles`, `profile_image_*`.
Preserve in a merge: the footer default (on for a tailored copy; upstream's Settings switch is opt-in, `footer_enabled === true`, and the section exists for tailored copies only, the fork's reads ON until the field is false and exists for every résumé), the profile-image switch beside it (both are the shared `Switch`, as upstream's "Page footer"), the band reserved for it (0.4in), `break-inside: avoid` for entries, custom and added headings, the Professional templates, the Word export guards and order. Review with care: any change by upstream to a template's `@page` margin or `.page` rules (the override reads the margins and replaces only the bottom), to `_render_html`, to `_build_docx` and to `export_pdf`'s margins or footer. After a merge, besides the checks above: `pytest backend/tests/test_resume_template_ownership.py backend/tests/test_resume_template_print_layout.py backend/tests/test_resume_template_header_title.py` (upstream's two template tests run unmodified except that print_layout skips templates that lay out their own pages) and a look at one generic and one Professional PDF.

## [Unreleased]

### Added
- **Regression tests for the template overrides and the Settings switches:** `test_resume_template_override_detection.py` (a rotation of the default heading names on all ten templates, one layout block per official template, comments, strings and partials in a template lab) and `resumeSettingsSwitches.test.jsx` (shared Switch, defaults, fields, keyboard, disabled image switch, section availability). 19 deliberate bugs in the backend mechanism and 10 in the Settings editor were each caught by at least one test.
- **Word export parity check against upstream:** `tests/tools/docx_parity.py` compares the fork's generic Word export with upstream's `_build_docx` on 22 inputs, including malformed ones, and exits 1 on a lost guard or a difference in text, links or headings. Run it after fetching upstream, before and after a merge.
- **Active/Inactive regression tests:** `backend/tests/test_resume_active.py` also covers company selection (a new inactive base is refused, a stored one dropped), company scoring texts, the default résumé until it is reactivated, tailored copies of an inactive base, and the intended exceptions (seeding and the account copy).
- **Golden regression tests for the fork's résumé output and the API surface:** `backend/tests/test_fork_golden.py` compares every template's rendered HTML (hash), the structure of the Word export (text, run and paragraph properties, links, page setup, footer, image sizes) and each route's methods, path and dependencies with `backend/tests/fixtures/fork_golden_*.json`, so a merge or refactor that changes any of them fails the test run with the first differing entries. Regenerate deliberately with `python -m backend.tests.fixtures.generate_fork_golden`, the same way as `location_golden.csv`.
- **Active/Inactive base résumés:** each base résumé card on `/resumes` has the same Active/Inactive pill as `/companies`. Active bases are listed first; an inactive base is dimmed there (its tailored copies stay) and disappears from every picker: tailor, cover letters, applications, the default-résumé and company résumé selectors, the sidebar count and score runs. The API refuses an inactive base as a tailor/copy source, default résumé or company selection (an already-stored id is left alone and simply ignored). Existing résumés stay active.
- **Select & style for the Professional résumés:** a "Select & style" button in the résumé preview swaps the PDF for a clickable view of the same template. Click the page, the profile image, a section or any part of one (a heading, a job's title, its dates, description or bullets, a skills label, a school…) and a panel sets that part's font, size, line height, colour, bold, italic, alignment, case, letter spacing, margin and padding; a heading also takes its rule line, bullets their character and indent, the page its margins and the image a width and height. A change applies to every instance of the part. "Back to PDF" shows the exact print layout.
- **Margin and padding on every section and card:** each section (Header, Summary, Experience, Skills, Education, Projects, Publications) takes margin and padding on all four sides, and the repeating blocks (one job, school, project or publication) are selectable cards with the same properties as any other part. In the PDF they are plain CSS; in Word, where there are no boxes, they become space before the first and after the last paragraph and an indent on every paragraph of the section or card.
- **Manrope font:** the Professional templates ship Manrope (seven weights, `fonts/Manrope-*.ttf`) and the style panel lists it beside the other fonts. The PDF embeds it only when a section or part uses it (about 0.9 MB of extra HTML for that render; résumés that never pick it carry nothing). Word has no font embedding here, so a Word file names "Manrope" and shows it only where it is installed. The 14 `.ttf` files (seven weights in each of the two Professional template folders) are committed even though `.gitignore` lists `*.ttf` for the licensed Garamond fonts, so a new font file needs `git add -f`.
- **Style saved with the résumé and applied to both exports:** values live in `json_data.style`, are validated server-side (fixed font list, `#RRGGBB` colours, clamped numbers) and print in the PDF and the Word export. Other templates ignore them; a template opts in with `"style_overrides": true` in its `meta.json` (see CONTRIBUTING.md).
- **Style in Word exports:** margin and padding become paragraph spacing and indents (Word has no padding; a heading's bottom padding is the gap above its rule line), letter spacing rounds to Word's units, a picture is centre-cropped to the chosen width and height like the PDF's cover crop, and heading paragraphs keep their XML in the order Word requires.
- **Professional résumé templates with a profile image:** Professional (Top-Left Image) and Professional (Top-Right Image), two PDF templates in the ATS reference style (Arial, `#232323` text, ruled `#1F4E79` section titles, "Title - Company" entries) with an optional 100 px profile image. The picture is uploaded once in Settings › Resumes (`POST /settings/profile-image`, stored globally) and used by every résumé; a "Show profile image" switch in a résumé's Settings section turns it off. Each account keeps its own picture (it is a per-account setting, never inherited from the owner).
- **Editable Word export:** the résumé editor's Download menu offers PDF and Word (.docx). The file is real text (hyperlinks, tab-aligned rows), so it stays editable and ATS-friendly. The Professional templates get a styled Word file with the picture beside the name; custom section headings and the footer carry over. The export uses upstream 3.0's helpers: text is cleaned of XML-illegal control characters, `tel:`/`mailto:`/web links stay clickable, downloads keep non-Latin names (`filename*=UTF-8''…`), and a 503 explains a missing python-docx.
- **Tailored PDF footer:** every page of a tailored résumé PDF ends with "Candidate Name - Job Title - Company" in small light-grey text, with its own reserved band so content never runs under it. A "Show footer" switch in the résumé's Settings section turns it off (on by default; tailored copies do not inherit a base résumé's choice). Unlike upstream 3.0, where the footer is opt-in, it stays on by default in this fork; the linked job is read only from the current account.
- **Custom section headings:** Summary, Skills, Experience, Education, Projects and Publications each take an optional "Header title" in the résumé editor and Persona. It replaces the heading in every template's PDF and in the Word export; empty keeps the template's default. Upstream's Modern Professional template follows it too.
- **Duplicate** in the base résumé menu and the tailored-copy menu creates an independent base résumé with the same content (Rename is upstream's inline top-bar rename).
- **Delete jobs with what hangs off them:** "Delete" in a feed row's menu and in the bulk bar removes the job with its tailored résumés, cover letters and applications (`POST /jobs/bulk-delete`). Base résumés and LLM cost logs stay, only unlinked from the job.
- **Scrape all:** a button in the Searches header runs every search once, disables itself while the scrape is active and reloads the list when it finishes.
- **Two isolated Docker instances:** `docker-compose.alish.yml` and `docker-compose.elsa.yml` override the base file with their own project name, ports and named volumes so the instances cannot mix; each also runs Adminer for PostgreSQL, and Elsa's file sets its own network.

### Changed
- **Résumé Settings use the shared Switch:** "Page footer" and "Profile image" are `Switch` controls (they were checkboxes), with upstream's footer label, hint and helper line. Fields, values, defaults (ON until the field is false), the disabled image switch for a template without a picture, and the section for every résumé are unchanged.
- **Official résumé templates back to upstream:** seven of the eight (`garamond_alt`, `inter`, `modern`, `montserrat`, `palatino`, `raleway`, `traditional`) are upstream's own files again; the PDF print layout (footer band, entries not split across pages) and custom section headings, including the optional Summary heading, are applied by the renderer. Compared in Chrome on a 4-page résumé with and without footer and with custom headings: the same text on every page and identical vertical positions; text sits up to 0.6pt (0.2mm) further right. Upstream's `test_resume_template_header_title.py` runs unmodified, and `test_resume_template_print_layout.py` differs only in skipping templates that lay out their own pages.
- **Settings section of a résumé** keeps only the "Show profile image" and "Show footer" checkboxes; all styling is done through Select & style.
- **Profile image upload:** files up to 10 MB are accepted (was 2 MB), and the stored copy fits 300×300 px (was 120×120) so the image-size option stays sharp.
- **Professional templates and the Word builder kept in step:** both templates and the shared Word builder use smaller meta and description text (8.5 pt), a bold title with the company in normal weight, and a 100 px picture, so PDF and Word match.
- **Repository:** `.gitignore` also ignores `.DS_Store`, `tmp/` and `misc`.

### Fixed
- **Custom section headings no longer chain:** a title equal to another section's default name ("Experience" for Summary, "Career" for Experience) printed the second title on both headings in every official template; they are swapped in one pass now.
- **A comment can no longer switch the fork's template behaviour off:** whether a template handles the footer band or the headings itself is decided by Jinja's parser, including partials, not by searching the source for the variable names.
- **Word export no longer fails on malformed résumé data:** a string or null where an experience, education, project, publication or skills entry belongs, a skills object without a category, or a number in a text field (summary, title, company, dates, school, bullets, URL) is skipped or printed as text, as the PDF and upstream's export do, instead of returning a 500. An empty Skills heading and a `None:` label are no longer printed.
- **Word section order follows the template:** the eight generic templates list Experience before Skills in Word, as in their PDF; the Professional templates keep Skills first. The order comes from the key order of `docx.titles` in a template's `meta.json`.
- **Stylelint is clean:** the Select-and-style preview frame uses the `--iframe-bg` token and the native colour input carries the project's `lint: allow` exemption.
- **PDF page margins on every page:** all résumé templates keep their top and bottom margin in `@page` (and reserve the footer band there), so page 2 onward is no longer flush with the paper edge. Upstream's Modern Professional template got the same footer band and print rules, and upstream's print-layout test now checks this layout.
- **Word exports include the footer** of a tailored résumé.
- **Word export hardening from upstream 3.0:** a résumé whose header is null or a string, whose contact list is not a list, or whose contact text or address is a number no longer fails the export; a skills list prints as `Tools: Jira, SQL` instead of a Python list; and the file's author is the candidate, not "python-docx". Upstream's Word tests run against the fork's builder in `backend/tests/test_resume_docx_upstream.py`.
- **Word export input checks:** an unknown template is rejected with 422, and an invalid stored profile image is skipped with a warning instead of failing the export.
- **Deleting a job unlinks `job_runs.target_job_id` explicitly,** so SQLite, which does not enforce `ON DELETE SET NULL`, behaves like PostgreSQL.
